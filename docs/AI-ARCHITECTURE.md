# AI architecture

Nuzky is built around AI the user brings: any MCP-capable agent can edit a project, live in the open app, and the in-app AI panel runs the user's installed Claude Code, Codex or OpenCode under their own login. People without any of them sign in with their ChatGPT account in Nuzky itself, and the panel runs ChatGPT on their plan. Gemini runs only in the user's own terminal, as Google's Antigravity CLI, which Google lets no other app start (Gemini, below). Connect agent covers Claude Code, Codex and Antigravity CLI in a terminal, and copies the same server for Claude, Cursor, OpenCode and any other agent. Research behind these decisions: [docs/research](research).

Decided on 6 Oct 2026 after two independent proposals and a cross-critique, and refined the same day after the headless MCP landed (two more proposals and a cross-critique).

## Principles

- **One editing authority.** Every change, from the UI, an agent or the CLI, goes through `ProjectSession` and the existing `EditCmd` validation. Agents never write the project JSON directly.
- **Live, reversible runs.** An agent's changes appear in the app as they happen. A whole run is one undo step. Review is available but never required to finish a run.
- **Deterministic primitives, creative agents.** Timing-critical work (ripple cuts, caption timing, transcripts) is done by engine tools; the agent decides what to do and checks rendered frames.
- **Local first.** Editing, analysis, transcription and export run on the machine. A cloud model only sees what Nuzky sends it: prompts, tool results, transcripts and frames. The panel's agents may search the web only with their provider's own search, which runs on the provider's servers, with queries of the few words a request needs (AI panel, Web search).

## Processes

```
Claude Code / Codex / Gemini / Cursor ──stdio──▶ nuzky-app mcp --project P ──IPC──▶ Nuzky app (Host for P)
                                                         │
                                                         └─ no app running: its own Host for P
```

- `crates/session` holds `Host`: the `ProjectSession`, the one job system and the transcript store. The app owns one shared Host; each connected MCP client has a separate access level and run ownership. A headless bridge creates its own Host. The desktop export/captions/transcript jobs still use `src-tauri/src/jobs.rs`; migrating those jobs is separate work. `ProjectSession` owns the live `Editor` and its history, revision, session epoch, the open run, the writer thread and crash recovery. It has no Tauri dependency.
- The bridge is `nuzky-app mcp --project <path> [--allow-write]`, handled before Tauri starts, so agents run the installed app's own version; `nuzky mcp` is the same code for development. The bridge serves the MCP catalog, guide and schema itself and sends each tool call to the app, or to its own Host when no app owns the project.
- IPC: a local AF_UNIX socket, `$XDG_RUNTIME_DIR/nuzky/<project-hash>.sock`, on every system; Windows has had AF_UNIX since Windows 10 version 1803 (`uds_windows` wraps it). Newline-delimited JSON: a hello `{nuzky: 1, token, client, access, current, conversation}` answered with the session epoch, then `{id, tool, args}` → `{id, result}`. The 32-byte random token is hex-encoded in `<project-hash>.token` next to the socket and rewritten on every open; it is read without following links and must be exactly 64 hex digits. Each side checks that the other runs as the same user before it sends anything: the peer's uid (`SO_PEERCRED`, `getpeereid`) on Unix, on Windows the user SID of the peer's process (`SIO_AF_UNIX_GETPEERPID`). On Unix the directory is 0700 and both files are 0600, and without XDG_RUNTIME_DIR the directory is `<temp>/nuzky-<uid>`. On Windows the directory is made with an access list of one entry, this user, owned by this user also when Nuzky runs as administrator, and every check requires exactly that; the files in it take its list. Without XDG_RUNTIME_DIR it is `nuzky-ipc` in the user's own temp folder. Nothing listens on the network.
- Access is per client: a read-only client never takes the lock and mutating tools return `READ_ONLY`. It may cancel a job it started itself, such as a long `activity`.
- Agent access is the app's, not the client's: `current: true` in the hello (a bridge started with `--current`) is refused with `AGENT_ACCESS_OFF` while it is off, and turning it off shuts those connections within the listener's 20 ms round, so their open run ends kept and their jobs stop. Clients that name the project's path (the AI panel's agent, `mcp --project`) do not depend on it. It is not a security boundary: any process of the same user can read the token. It is the user's switch for agents they set up once and forget. Code: `crates/mcp/src/ipc.rs` (`Listener::start` takes the flag), `src-tauri/src/connect.rs` (the flag and its setting).
- A client's jobs stop when it disconnects. The AI panel's agent connects anew every turn, so the app begins a conversation in the Host's jobs and gives the panel's bridge its id in `NUZKY_CONVERSATION`, which the hello carries. A connection that names a conversation the app began starts and cancels jobs as that conversation, so they run on after the turn ends and the next turn can read or cancel them; any other id is ignored. A reframe still stops with the turn, because it writes into the turn's run, which ends then. Stop in the panel, Stop and edit while the panel's agent answers, and a new conversation stop its jobs, and a late call of the stopped turn's bridge cannot start more; the next turn starts its jobs under a new id. Another project and quitting stop every job. Code: `src-tauri/src/agent_panel.rs`, `crates/session/src/jobs.rs`.
- Ownership is an OS lock on `<project>.lock`. A writable headless bridge currently holds it for its lifetime. A bridge started with `--project` chooses app IPC or headless once at startup; if an attached app closes or switches project, later tool calls return `APP_CLOSED` and require restarting the agent's MCP server. A bridge started with `--current` attaches at its first tool call and again at the first call after the app let go (below). Releasing an idle headless lock and retrying read-only app opens are planned.
- The session reports changes as events on a channel, never calling out while holding its lock. The app forwards them to the preview and the frontend, which ignores snapshots older than the one it has within the same session epoch. The revision changes only when the project does.

## Runs and undo

A run groups one agent turn. There is one linear history: a run is one entry in it, between the user's own edits.

- `begin_run(label)` seals the history, writes `<project>.checkpoint.json` and returns `run_id`. Mutations are only accepted from the run that owns the session. Manual edits, Undo and Redo in the UI are blocked with "AI is editing · Stop"; the toast offers "Stop and edit", so stopping the AI is always deliberate.
- `apply_edits(run_id, request_id, edits[])` applies a batch atomically to the live project under the run's coalesce key `run:<id>`, so the whole run merges into one undo entry. A repeated `request_id` with the same content returns the stored result; with different content it is an error. The result lists created, changed and removed clip ids and, in `clips`, the created and changed clips in full with their real times after magnetic repacking. It is returned only once the project is on disk. When those clips would take more than 8,000 characters, as when an agent restyles every caption, the MCP tool leaves `clips` out and gives their count in `clips_omitted`, so the answer stays short enough for an agent to read; `get_state(clip_ids)` reads them. A retry gets the same short answer.
- Text in a font this computer does not have is drawn in Inter, and the project keeps the name. apply_edits, build_captions and make_reels add `warnings`, one per missing font, from the fonts the call itself gives text: the styles in the edits (text, captions, pasted clips and attributes, track restyles, cover texts), the captions' resolved style, and the text of the reels made. A retry with the same `request_id` repeats them; moving or cutting existing text adds none. get_state's `missing_fonts` lists the missing fonts of the whole project. Both ask the renderer's own lookup (`TextRenderer::has_family`: bundled and installed families, exact names), loaded once per process; the CapCut draft importer matches names the same way.
- `end_run(run_id, keep | discard)`: keep seals the entry; discard drops it without a redo entry. A run also ends with keep when its client disconnects or after 2 minutes without calls from that client; reads by the UI or other clients do not keep it open.
- Stop in the UI revokes the run first (late calls get `RUN_STOPPED`), cancels its jobs, then ends it with keep. Ctrl+Z then undoes the whole run and Ctrl+Shift+Z brings it back.
- `undo_run(run_id)` works only while that run is the last history entry.
- Versions outlive the session. Each kept run, each user step (one undo entry), undo, redo, restore and the project as it opened becomes a version: the project's compact JSON, its SHA-256, a label, the time and the run id. A step with a coalesce key (a drag, a typing burst) becomes one when the next step starts, and until then `list_history` shows it first under the index it will get; an open run becomes one when it ends; a discarded run never. The writer thread appends them to `<project>.history.jsonl`, one JSON line each, after the saves before them; a line whose project an earlier line holds leaves it out. The newest 200 versions and 32 MiB of distinct project JSON are kept, and once the file holds twice that it is written again atomically with only those. Reading skips a torn or unreadable line and a line whose project no longer matches its hash, and the next write replaces the file; a versions file that is a link is never read or written through, only replaced. A failed write shows as "Not saved" until a later one succeeds. A project that opens different from its newest version (an older project, or a save that never reached the file) becomes the version "Opened".
- `list_history(limit)` lists the versions newest first with the current hash. `undo_to(index | hash prefix)` validates the stored project and replaces the current one as one undo step; it needs no open run (`RUN_ACTIVE`), like Undo in the app.
- Every result carries `revision` and `session_epoch`; mutations may pass `expected_revision` to fail fast on stale state.
- User edits are saved shortly after they stop; run batches are saved before they are acknowledged.
- On open, a leftover checkpoint means a run did not finish: the app asks to keep the AI changes or restore the version before, as an undoable edit. Headless mode refuses writes until that is resolved.
- Agents never set the user's selection.

## Transcripts

- A transcript belongs to a media file, not to a timeline: words with times in the file's own (source) time, stored once in `<data dir>/nuzky/transcripts/<fingerprint>.json`. The fingerprint hashes the file size, its first and last MiB, and 32 evenly spaced 64 KiB chunks. The same file in several projects is recognised once and a moved file keeps its transcript. Version 2 records also store duration_us; version 3 records also store `alignment`, the word timing model that measured the words (null when they are Whisper's estimates). Version 2 records still read, as estimates, so an existing transcript and the word corrections keyed by its words stay; version 1 records and duration differences over 1 ms are treated as missing.
- Whisper's word times are estimates, 100–300 ms off in connected Czech speech. Right after recognition, `transcript::recognise` measures them in the sound with the word timing model of the recognised language (`nuzky_analysis::Aligner`, a wav2vec2 CTC model with Viterbi alignment of Whisper's text; Czech and English), downloaded on first use with a pinned SHA-256 like the Whisper models, and the record stores those times. The job shows the download ("Downloading word timing model" in the app, `downloading_word_timing_model` for agents) and the measuring ("Measuring word times", `measuring_word_times`); a stop ends either within a second. Without a model for the language, offline, or when the model fails to load, the words keep Whisper's estimates moved into the nearest pause by `nuzky_analysis::align_words` (a pause wins over a consonant's closure; without one, the quietest moment within 60 ms), as before; `transcribe` reports `word_times: "estimated"` instead of `"measured"`. Words the model cannot spell (numbers, acronyms) share the gap between their measured neighbours. Existing transcripts are not measured again, since word corrections are keyed by a word's start; recognising a file again measures it. Cut margins, pauses and captions all count from the stored times.
- What the timeline says is always derived: `engine::speech::map_words` maps the words of every heard clip (unmuted track, volume above 0, a video asset with sound, detached sound included) through its source range and speed. Cuts, slivers, speed, undo and redo are therefore always right, and a transcript never goes out of date; the only note left is "N clips not transcribed".
- `get_transcript` and `edit_transcript` use `transcript_key`, which includes recognised words as well as their timeline layout. `get_state` exposes `speech_layout_key`; `apply_edits` accepts it as `expected_speech_layout_key`, a hash of exactly what `map_words` reads. The session rejects it with `SPEECH_CHANGED` when the speech moved in the meantime, and accepts it after unrelated edits such as a caption restyle.
- Misrecognised words are corrected in the project, not in the shared store: `word_corrections` lists the media file, the word's start in it, the recognised text and the correction. Deriving applies them to the source words before `map_words`, so `get_transcript`, `analyze retakes`, captions built again and the app's transcript all read the corrected text. A correction applies only to the word with that start and recognised text: after the file is recognised again differently it does nothing and never lands on another word. `CorrectWords` sets them; the app and `correct_words` plan it once (`plan_correction` in `crates/mcp/src/transcript.rs`) together with the caption clips that show the word, as one undo step. Each correction can name the text the word reads now (`expected`); when one word reads otherwise, the whole batch is refused with `WORD_MISMATCH` before anything changes, so an index off by one cannot overwrite a neighbouring word. The app always sends it.
- Tracks have `keep_in_place`; `RippleDeleteRanges` without `keep_track_ids` uses it, so agents cut the way the UI does and leave music alone.

A plugin without a script only adds effects, so its manifest has no `needs`, `inputs`, `sections`, `actions`, `files` or `tools`, and running it fails with `PLUGIN_NO_SCRIPT`. No run, no project change; needs write access. `get_state` lists the effects the project is drawn without in `effect_issues`, and an export that drew without one says so in `warning` |
| `run_plugin(id, inputs, run_id?, selection?, playhead_us?, dry_run?)` | Runs the plugin's `run(ctx)` as a job of the caller's run in a fresh QuickJS runtime without modules, files, network, timers or processes (256 MB, 1 MB of stack), with `ctx` the get_state project, the checked inputs, the selection, the playhead and, when the manifest needs them, the get_transcript words and the silences, loudness and beats `analyze` finds in the sound of every media clip with sound, placed on the timeline through each clip (`crates/mcp/src/plugin_data.rs`; found once per prepared sound and kept in memory, and prepared first within the job when the sound is not, which Stop cancels). The script and the check of its edits on a copy of the project run in a separate process: Nuzky's own executable started as `plugin-sandbox` with an empty environment except `LD_LIBRARY_PATH` on Linux and `SystemRoot` on Windows, which gets the script, `ctx` and the project on stdin and answers the edits and the project after them, or why they do not apply, on stdout, with the progress on stderr. That process is killed above 1 GB of memory (`PLUGIN_OUT_OF_MEMORY`; `RLIMIT_DATA` plus a watchdog of its resident memory every 10 ms on Linux, the watchdog on macOS, a job object on Windows), within moments by Stop or `job` cancel, and after 60 s, so edits that would copy gigabytes fail there and never reach the memory of the app or the MCP server. Only then do its edits (at most 5000) apply, as one batch of the run, all or nothing; `addAssets` and reel candidates pointing at a new project file are refused. The plugin's own pictures and sounds, listed by plain file name in the manifest's `files` (API 2), are read from its folder without following links (no symlinks, no hard links), at most 20 MB, copied into `<data dir>/plugin-files/<hash>.<ext>`, measured with `media::picture_size`'s limits when a picture and probed (`crates/mcp/src/plugin_files.rs`); `ctx.files` gives their asset ids, and the ones its edits name join the batch as an `addAssets` ahead of them. So a project a plugin edited never refers to the plugin's folder or to a file the script chose. A dry run applies them to a copy and answers the edits, the files they would add (`adds`), message, log and whether they apply. `run(ctx)` may also return `tools`, at most 20 calls `{tool, args}` of `build_captions`, `apply_zooms` and `apply_motion` (`crates/mcp/src/plugin_tools.rs`), each allowed only when the manifest's `tools` (API 2) names it, else `PLUGIN_FORBIDDEN_TOOL`; their arguments are read by the MCP tools' own types, with `run_id` and `request_id` refused. In the job, after the sandbox answers, Nuzky plans them in order on the project the plugin's edits left with the MCP tools' own planning (`tools::caption_plan`, `zooms::ranges`, the engine's `applyMotion`), in the plugin's own process after its edits, within its memory limit, its 60 s and Stop, and appends their edits to the plugin's batch, so a call that fails keeps nothing. None of them transcribes, downloads, decodes or prepares sound: they read the stored transcripts (found by a fingerprint of samples of the project's own media files), the sound already prepared in the cache, the creator's `EDIT.md` and the saved caption styles; the only download on these paths, the word timing model, belongs to `transcript::recognise`, which only `transcribe` and the app's recognition job call. `apply_zooms` checks its `transcript_key` against the project after the plugin's edits; `ctx.transcriptKey` numbers `ctx.words`. An agent's dry run plans the calls on the copy too; the app's preview only checks and names them, so it costs the same however long the transcript is. The app runs a plugin in a run of its own labelled `Plugin: <name>`, kept as one undo step, or discarded on an error or Stop |

`RippleDeleteRanges { ranges, keep_track_ids? }` cuts the ranges out of every track except the kept ones and closes the gaps, so video, overlays, audio and captions stay in sync. `AddCaptions` never deletes other tracks. `ZoomRanges { ranges: [{startUs, endUs, scale}] }` splits main-track clips at the range edges and multiplies the scale of the pieces inside, keeping position and rotation; an edge that would leave a piece under 0.3 s, or cut a transition, animation or fade short, moves to the clip's edge, split halves play their sound on unchanged, and clips with keyframes are left alone and listed in the outcome's `skipped`. `SetThumbnail { thumbnail }` replaces the project's thumbnail of its format, its `overlays` included (images of the project drawn over it, such as a logo), and `RemoveThumbnail { format }` removes it; `RemoveAsset` takes the asset off every thumbnail's overlays; `RippleDeleteRanges` moves a thumbnail's frame time with the picture, so it keeps showing the same moment. `ReplaceMainClips { clips }` puts video and picture clips on the main track in place of all its clips, back to back from 0 with new ids, and moves nothing else. `SetReelCandidates { candidates }` replaces the reel candidates and `UpdateReelCandidate { candidate }` replaces the one with its id; validation keeps those not made yet apart, with single-line texts, and a made one with an absolute project path. Their words and times stay as proposed, so a candidate whose speech moved since is refused by `make_reels` with `SPEECH_CHANGED` instead of cutting the wrong words.

Resources: `nuzky://guide` (the editing skill), `nuzky://plugin-guide` (writing plugins), `nuzky://schema` (project JSON schema) and, when the creator has one, `nuzky://style` (their `EDIT.md`). Prompts: `edit_selected(goal)`, `thumbnail(wishes?)`, which picks the frames, writes a hook from the transcript and makes, checks and exports both covers in one run, and `rough_cut(wishes?)`, which runs the whole way from raw takes to an exported reel (in Claude Code: `/mcp__nuzky__rough_cut`).

## Creator style

- `nuzky style learn <recording> <cut>...` turns pairs of a raw recording and the creator's finished cut into `<data dir>/nuzky/EDIT.md`: what gets cut (restarted sentences, repeats, slips, fillers, dropped passages, calls to action), pauses, pace, cuts, captions and zoom, each rule in numbers and shown on the moments of the recordings it comes from, at least three. A closing call to action, talk before the start and talk after the end need one, since a video has at most one of each. Calls to action count both the ones the cut removed (any sentence near the end with a word such as like, save or link) and the ones it kept (only a plain ask such as "follow me" or "leave a comment", because a false keep would overrule the guide), and the more common choice is the rule; kept as often as cut is a rule too, saying there is no clear preference, so the guide's default applies. Rarer things are listed as seen, not as rules. The same input always gives the same file, and an existing file is only replaced with `--replace`, since the creator may have edited it. Written to the default place, it becomes a version of the style (below) and keeps the creator's own rules; `--out` elsewhere writes the plain file.
- `nuzky style learn --from <timeline.otio or CapCut draft folder>` learns from timelines the creator cut in another editor instead. `crates/interchange` reads a timeline file into a neutral `ImportedTimeline` (tracks, media clips with their source in and out, place on the timeline, speed, volume, framing and keyframes, transitions, text clips and markers) and lists in plain words what it did not read; each format has its own module. OpenTimelineIO's JSON is read with serde alone (`otio.rs`): every `RationalTime` is turned into microseconds at its own rate, media with a timecode counts from its available range, a time warp changes how much media a clip plays but not its length, gaps and nested sequences keep their time, and only local files are media, so a web address or a share on another computer in a shared file is never touched. OTIO has no standard for framing, volume or titles, so those are not read from it. A CapCut draft is a folder (`capcut.rs`): its timeline is `draft_content.json` on Windows or `draft_info.json` on macOS, plain JSON in CapCut International, where each track's segments name their material by `material_id` and every time is in microseconds. It reads the cut (`target_timerange`, `source_timerange`, `speed`, a speed curve as its average), volume, a muted or hidden track, framing (`clip.scale`, `clip.transform` in halves of the frame with y up, `rotation`), `common_keyframes` (timed in the media's own time, from the file's start) and captions with their place and look (font, size at 5.1 px per CapCut size unit on a frame 1080 px across its shorter side, colour, bold, outline), and maps the most common transitions by name (dissolve, fade to black, zoom, slide) with the rest as another transition. Media missing where the draft says is looked for in the draft's own folder, where CapCut keeps copies under `##_draftpath_placeholder_…##`. JianYing encrypts its drafts: such a file is recognised and refused with what to do instead, never decrypted. `style/from_timeline.rs` turns the timeline into what learning reads: each recording whose sound the timeline plays (on its audio tracks, or else its lowest video track; video above that is B-roll) is a source of its own, its clips on the tracks that play its sound (a clip that only repeats another, such as a second channel, left out) are the pieces with a full match, the recognised words are moved through them as `map_words` does, and pauses are gaps of 80 ms or more between words, a gap where another recording speaks being no pause. The finished video is the whole timeline, its gaps and B-roll shared among the recordings by how much each plays. A piece maps cut time to the recording one to one, so for a sped up clip only its start is exact, while its words are placed at their speed. A timeline that says where its pictures and captions sit, as a CapCut draft does, gives the picture straight from it: framing every half second of the recording's clips on the lowest video track that shows it, zoom changes at cuts and between keyframes, and the look most captions are drawn in; nothing is measured in pixels. A recording played whole teaches no cutting. In the app, Learn my style does the same with Projects (.otio) and CapCut and shows `EDIT.md` as learned; nothing is kept until the creator uses it, which writes the style through `Store::replace` only over the version the preview was made over (over an existing style only after they agree) and keeps the evidence.
- A CapCut draft also opens as a project of its own, so a creator moving from CapCut keeps working on their cut (`crates/mcp/src/import.rs`, the app's `open_capcut_draft`, `nuzky new <project> --from <draft folder>`). The draft is read as for learning, but whole: hidden and muted tracks stay hidden and muted, photos are image clips, sound fades come along, captions CapCut made from speech (`subtitle` texts) go to the Captions track and keep their wrap width (`line_max_width` of the frame's width, before the text's scale). `Read::played` then leaves hidden tracks and photos out and silences muted tracks for learning, as before. Each file a clip names is probed once, only when it is a regular file; one that is missing or does not open gets an asset shaped as the draft says, so its clips keep their place without picture or sound and nothing after them moves. The lowest video track becomes the magnetic main track when it runs back to back from zero, as CapCut's does; otherwise its clips go on an overlay track. Clips a hair over each other start where the one before ends, larger overlaps get tracks of their own. Dissolve, fade to black, zoom and slide map to Nuzky's; any other transition, CapCut's effects, filters, colour adjustments (only those switched on: a value other than 0, and automatic colour only with `enable_smart_color_adjust`), voice settings (noise reduction only with `is_denoise`, Enhance voice and Normalize loudness only when enabled), animations, masks, chroma key, canvas backgrounds, crop, flip, opacity, text shadows, backgrounds, alignment, letter spacing, words in other colours and fonts this computer lacks are listed once per kind with how often, in `Project.imported` (`editor`, `path`, `left_out`), which get_state shows. The project is built directly, normalised by one engine edit (packing, empty tracks, fades and transitions longer than their clips) and validated before it is written; the draft is only read. JianYing's encrypted drafts are refused with what to do instead. Opened from the app, a dialog shows the list with Finish with AI, which asks the panel's agent to finish the draft; the guide's Finish a draft section tells it to keep the creator's cut and carry on in their style.
- The style lives beside `EDIT.md` in `<data dir>/nuzky/style/` (`crates/mcp/src/style.rs`). `evidence/` holds what was learned from each video, enough to learn everything again: the recording's and the cut's words, where the cut's pieces came from, its pauses, captions and framing. Learning the same video again replaces its evidence, and the newest 12 videos are kept. `nuzky style learn` into the default place keeps the evidence of the videos it learned from the same way, so Your style shows how well they back each rule and later learning builds on them; `--out` elsewhere keeps none. `versions.jsonl` holds every version of the style, newest last: the text, what each accepted rule decided and which rules learning leaves alone. Learning only adds evidence and never writes `EDIT.md`; the rules learned from all evidence that are new, or whose decisions (a pause length, the filler words to cut, caption limits and look, zoom; numbers, such as a caption's size, within 15 % or a small floor count as the same) differ from what was accepted, are suggestions. Accepting one writes its section and its Settings rows into `EDIT.md` where `learn` would put them, so accepting everything learned from some pairs gives the same bytes as `nuzky style learn` on them. Rejecting, removing or reverting a rule, or changing it by hand, makes learning leave it alone until the creator asks to learn it again. Under `## Your rules` the creator writes their own instructions; learning never touches them. A change made to `EDIT.md` outside Nuzky is recorded as a version too. Every writer holds `style/lock`; the version is written before the file, and a file not written yet is finished by the next change.
- Nuzky learns by itself, on this computer only, after every export (in the app and through `export_video`) and 10 s after the user's last edit of a project an AI run cut and the run was kept (or when the project is switched or closed before then). It reads the project, not the exported file (`project_evidence`): the recording is every transcribed video the project hears, one after another; the words its heard clips play and where are exact, from `map_words`; each heard clip is a piece; pauses are gaps of 80 ms or more between words; captions and the look most of them are drawn in (font, size and outline for a frame 1080 pixels across its shorter side with each caption's scale, colour, box, highlight, key words, case, shadow and spacing, which the style's `build_captions style` setting then holds) come from the Captions track, framing and zoom from the main track's transforms and keyframes, and the words the user corrected become the Spelling rule, each only when corrected to the same word every time and more often than left as heard, since the rule corrects it wherever it is heard, which `nuzky style learn` never writes. Nothing is learned while an AI run is open, from a project that plays everything it recorded, or from one that teaches exactly what the AI's last kept run left: the AI would only learn its own cut. Edits that undo the run teach nothing either, while an export of the user's own cut from before the run does.
- `EDIT.md` is parsed into blocks at the headings `learn` writes (`crates/analysis/src/style/doc.rs`). Anything else, such as the creator's own sections or a rule's subsections, belongs to the block above it.
- Where the cut came from is found by sound (`crates/analysis/src/style/align.rs`): the spectral shape of 20 ms windows, which a clip's own volume does not change, matched by a Viterbi path over candidate places in the recording. Retakes repeat the same words, so text alone cannot place a cut. A recording word counts as kept when its middle lies in a kept piece, or when the cut's own recognition heard the same word within a second of it: recognition times can be that far off next to pauses, where cuts are.
- Captions are found in the cut's picture as white pixels next to black ones, in the band where they are most common, and their words are counted from the gaps between them. Zoom and framing compare each moment of the cut with the same moment of the recording; scale, x and y are in Nuzky transform terms.
- The MCP server reads `EDIT.md` on each request, so an agent gets exactly the accepted style with the creator's own rules and never a suggestion. With it, the instructions, `nuzky://guide`, the prompts and the AI panel's ChatGPT give a short note, then the style, then the guide, so the style is what the agent reads first; `nuzky://style` serves it alone. Its rules override the guide's defaults, and the creator's own rules win over everything. The AI panel's own system prompt adds that the style decides how to cut, caption and zoom unless the user says otherwise. Without it, everything is exactly as before.
- `nuzky style compare <recording> <cut> <project>` scores a project by the recording's words: recall is the share of the creator's kept words the project plays, precision the share of the project's words the creator kept. It also lists the passages that differ.
- Recordings, transcripts and `EDIT.md` stay on the computer. An agent connected through MCP reads `EDIT.md`, which quotes the recordings, the same way it reads transcripts.

## Agent setup

The bridge starts with or without an app and attaches at its first tool call; after the app let go (the project closed, another one opened, Nuzky quit or Agent access was turned off), the first call fails with `APP_CLOSED`, so an agent never acts on another project unawares, and the next one resolves `current` again. With no project open a call fails with `APP_NOT_RUNNING` and with Agent access off with `AGENT_ACCESS_OFF`; the bridge never edits headless and never needs a restart, so one configuration serves every project.

Each file is backed up first, keeps every other setting with its value's original text and is left alone when it does not parse; a rule already there leaves the settings file untouched. An entry `agy mcp disable` turned off (`"disabled": true`) counts as not connected. ## Headless

Without the app, `nuzky-app mcp --project <path> --allow-write` (`nuzky mcp` in development) owns the project's session itself: the same tools, runs, undo history, versions, autosave and jobs as inside the app, and the same renderer for export. It needs no window, no display and no Agent access, which is the app's. This is the base for unattended work such as a watched folder (record, go to sleep, wake up to a cut reel), which does not exist yet.

- `nuzky new <project>` makes an empty project (`nuzky new <project> <media>...` one with the media on the main track), so a script needs nothing but the CLI to start.
- Verified on 11 Oct 2026 on macOS (Apple Silicon) by `crates/cli/tests/headless.rs`, on generated media with espeak-ng speech (`tmp-test/talk.mp4`): `nuzky new`, then over stdio `begin_run`, `import_media`, `apply_edits` addClip, `end_run` keep, `transcribe` and `job` until done, `get_transcript`, `analyze` retakes, `edit_transcript` as a dry run and then for real inside a run, `build_captions`, `end_run` keep, `export_video` with preset `reels` and `job` until done. The project file the bridge leaves has the cut and a Captions track, and `ffprobe` of the export shows H.264 1080x1920 at 30 fps with AAC and the project's duration within a frame. `scripts/check.sh` runs it with the other tests that need media and models.
- `nuzky render <project> <out.mp4> --preset reels` exports a project without an agent, with the same renderer.
- Transcription needs a Whisper model and the voice detector already installed in Nuzky's data folder, as the app installs them; `transcribe` answers `MODEL_MISSING` otherwise, telling the agent to have the user transcribe once in the app's Transcript tab. Nobody can be asked here, so it never downloads them. The word timing model downloads itself, as in the app.
- A writable headless bridge holds the project's lock until it exits, so the app shows the project as busy meanwhile. With the project open in the app, the same command attaches to the app instead (`--project` does not depend on Agent access).

## AI panel

Decided on 8 Oct 2026, replacing the ACP plan of 6 Oct, after an ACP spike ([research](research/2026-10-08-acp-spike.md)), two independent proposals and a cross-critique. ACP adapters are npm-only and need Node 22 at runtime, the Claude adapter is a product built on the Agent SDK, whose subscription terms are unclear, and codex-acp needed its own bundled Codex and let the user's MCP servers and a full-access title thread into the session. Driving the installed CLIs directly needs none of that.

Model and reasoning effort are optional per turn. Claude Code receives `--model` and `--effort`; Codex receives `-m` and `-c model_reasoning_effort="…"` on both `exec` and `exec resume`; ChatGPT receives its model slug and, when selected, `reasoning.effort` in the Responses request. No selection adds no flag or reasoning setting. `agent_models` lists the models Claude Code names in its answer to an `initialize` control request (a `claude -p` stream-json session with the user's settings, which point the aliases, but no hooks, MCP servers, tools or saved session; nothing reaches the model), without its `default` and once per resolved model, named with their version (when that fails, as with a Claude Code too old to answer, the aliases fable, opus, sonnet and haiku), Codex's installed CLI catalog from `codex debug models` (listed models in priority order), OpenCode's `opencode models --pure` lines (`provider/model`, with no reasoning efforts; run on the panel's own config folder, as a turn is, so a provider that only the user's `opencode.json` defines is not offered), or the signed-in ChatGPT account's models. Codex's catalog command does not accept `--ignore-user-config`. Claude Code names no default effort, so a model picked without one runs on the user's Claude Code setting. The lists expose supported reasoning levels and Codex's and ChatGPT's supported default, keeping only low to max: `ultra` delegates to other agents, which Nuzky turns off, and an unknown level could not be sent.

- **One process per turn.** `crates/agent` finds the agent (`NUZKY_AGENT_CLAUDE`/`NUZKY_AGENT_CODEX`/`NUZKY_AGENT_OPENCODE` override, `PATH`, then the usual install folders; on macOS `PATH` gets the folders the login shell's `PATH` adds, read once with `$SHELL -ilc`, and the agents run with it, since an app started from the Dock gets only launchd's `PATH` and a Node CLI such as Codex from vite-plus or nvm also needs `node`), starts it for one message (with Claude Code, also the ones sent while it works, below) and parses its output into `text`, `tool` (running, done, failed, with its arguments), `done {stopped}` and `error {code}` events; `src-tauri/src/agent_panel.rs` forwards them to React as `agent` events with the chat id. The next message continues the conversation with the agent's own resume (Claude `--session-id`, then `--resume`; Codex `exec resume <thread id>`, with the id it reports once it has kept the conversation, which a turn that failed before anything happened has not; OpenCode `--session <id>`, from the `sessionID` its event lines carry once it has answered). A turn that never got going starts a fresh session next time.
- **A message while it works** steers the agent (`agent_steer`). Claude Code reads messages as stream-json lines on its input, which Nuzky keeps open while it works, and takes one after the tool call it is on; at its `result` Nuzky closes its input, and Claude answers what is still on it as a follow-up turn of the same process before it exits (both checked with Claude Code 2.1.302 on 18 Oct 2026). ChatGPT's turn adds waiting messages to the conversation before its next request, and asks again with them instead of ending when they came with its answer. Codex `exec` reads one message per process, so once it has kept the turn (a finished reasoning step, message or tool call, as the resume needs), Nuzky ends its run as a disconnect does, so the jobs it started go on, and stops it, and the panel sends the message as the next turn, which resumes the conversation. ## ChatGPT sign-in

Added on 11 Oct 2026 as the first step of phase 6, after OpenAI's Sign in with ChatGPT for open-source apps ([overview](https://developers.openai.com/siwc/token-sharing-open-source), [sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions), [errors](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery), read that day). Someone without Claude Code or Codex in a terminal signs in with their ChatGPT account in Nuzky, without an API key, and the AI panel runs ChatGPT on it (AI panel, ChatGPT, above), with an agent loop on the Responses API rather than Codex app-server given the access token, which OpenAI's pages also describe: app-server would be another process to bundle, and its own tools to turn off.

- **Code:** `crates/chatgpt` signs in and keeps the sign-in, without Tauri; `src-tauri/src/chatgpt.rs` has the commands `chatgpt_status`, `chatgpt_sign_in`, `chatgpt_cancel_sign_in` and `chatgpt_sign_out`, and `src/components/ChatGptDialog.tsx` is the dialog. The frontend gets `ChatGptStatus` only (signed out with the last account's email and a notice, or signed in with the email and whether the plan is allowed), never a token. Nothing logs a token or the authorization address, which can hold the last ID token.
- **Flow:** Continue with ChatGPT first listens on `127.0.0.1` on a port the system picks (never `localhost`; only the port changes between sign-ins), then opens the system browser at `https://auth.openai.com/api/accounts/authorize` with a fresh `state`, OIDC `nonce` and PKCE S256 verifier for each attempt, `scope=openid profile email offline_access resource.invoke chatgpt.tokens.use.direct`, `resource=https://api.openai.com/v1`, `redirect_uri=http://127.0.0.1:<port>/auth/callback` and `ext_agent_host_id`. A first sign-in sends `client_id=dynamic_agent_client` and `agent_name_hint=Nuzky`; ChatGPT registers Nuzky with the account and workspace the user picks and puts the issued `client_id` (`oaiapp_…`) in the callback. Later sign-ins send that client id, the last ID token as `id_token_hint` (kept until signing out) and the email as `login_hint`, and `prompt=consent` when the last grant did not allow the plan. The listener answers only `/auth/callback`. A callback with another `state`, such as a tab left from an earlier attempt, gets a page saying it is out of date, and the wait goes on. `error=access_denied` ends the attempt as `SIGN_IN_DENIED`, five minutes without an answer as `SIGN_IN_TIMEOUT`, Cancel as `CANCELLED`; a new registration without a client id, or a returning one naming another client, fails. The browser tab says whether it worked once Nuzky has checked the answer. A listener connection that has not sent its whole request within two seconds is dropped, so a stalled local process cannot hold up the callback. When the browser cannot be opened, the error leaves out the launcher's own message, which quotes the address and with it the ID token.
- **Checks:** the code goes to `https://auth.openai.com/api/accounts/oauth/token` with the issued client id, the verifier, the same redirect URI and resource, and no client secret. The ID token's RS256 signature has to match a key from `https://auth.openai.com/.well-known/jwks.json`, read anew for each sign-in and checked with `ring` (already in the build for TLS), and `iss`, `aud` (and `azp` when present), `exp` (60 s of clock difference allowed), the nonce and a non-empty `sub` have to match. A returning sign-in whose `sub` differs from the saved one is refused as `WRONG_ACCOUNT`. Without `chatgpt.tokens.use.direct` among the granted scopes of the token answer, the sign-in is kept but shows "Nuzky can't use your ChatGPT plan yet", with Continue with ChatGPT to allow it and Sign out. A new account replaces the old one, whose session is revoked, only once it is valid, and only if the attempt was not cancelled or replaced by another one meanwhile; a Cancel that comes after the tokens were saved is too late, and the dialog then shows the account that signed in. A first registration keeps its issued client id before the exchange, so a retry after a failed exchange signs in to it rather than registering Nuzky again. Nuzky remembers one account at a time: after Use another account, returning to the earlier account registers Nuzky with it again.
- **Storage:** the tokens (access, refresh and ID token, expiry, granted scopes and the client id they belong to) are one JSON entry in the system keychain through the `keyring` crate 4.2 (Keychain on macOS, Credential Manager on Windows, the Secret Service on Linux), service `Nuzky`, account `ChatGPT <host id>`, so another data folder never reads them. Credential Manager keeps at most 2560 bytes in an entry, and the crate writes a password there as UTF-16, so on Windows the JSON goes as bytes into that entry and, where it runs longer, into `ChatGPT <host id> part 2`, `part 3` and so on; a save removes the parts a longer sign-in left after it, and signing out removes them all. `<data dir>/nuzky/chatgpt.json` (0600, replaced in one step) holds what is not secret: the host id (`urn:uuid:` and a UUIDv4, made before the first sign-in and kept for the data folder's life), the issued client id, `sub` and the email. OpenAI's page suggests a 0600 file for the tokens; Nuzky keeps them in the keychain instead, so no token lies in a file. Each read or change holds `chatgpt.lock` beside it, so two windows never renew the same rotating token at once. On Linux without a Secret Service (no GNOME Keyring or KWallet running) Continue with ChatGPT stops with `KEYCHAIN_UNAVAILABLE` before the browser opens; the keyring crate finds the store once per process, so a keyring started later takes a restart of Nuzky. On macOS the keychain asks once for the password when a build with another signature reads the sign-in: every ad-hoc build, and the first Developer ID build after an ad-hoc one. One Developer ID build after another reads it without asking, checked on macOS 27 (docs/BUILDING.md, Signing and notarization).
- **Renewing:** opening the dialog renews tokens that expire within five minutes (`grant_type=refresh_token` with the issued client id and resource, without `scope`, so the grant stays). The answer replaces the access token, expiry, scopes and the rotated refresh token in one keychain write. A refused refresh (`invalid_grant`, `invalid_refresh_token`, `token_expired`, `refresh_token_expired`, `refresh_token_invalidated`, `refresh_token_reused`, read from `{"error": code}` or `{"error": {"code": …}}`) removes the tokens, and the dialog says the sign-in ended; `invalid_client` also forgets the registration, so the next sign-in registers Nuzky again. Offline or after a 5xx everything stays and the next look tries again. Access tokens live an hour, refresh tokens 30 days from each refresh.
- **Signing out** revokes the refresh token at `https://auth.openai.com/api/accounts/oauth/revoke`, the `revocation_endpoint` of OpenAI's discovery document (three tries after a network failure or a 5xx), then removes the tokens; when OpenAI did not confirm it, the dialog says so and points to ChatGPT's settings. The host id, client id and email stay, so signing in again reuses Nuzky's registration; Use another account registers anew.
- **Network:** `auth.openai.com` only while signing in, when the dialog opens with tokens about to expire or the panel's ChatGPT needs a token for a request (`ChatGpt::access_token`), and when signing out; `api.openai.com` only for the panel's ChatGPT, its model list (loaded while ChatGPT is the panel's agent) and its answers. The panel itself reads the stored sign-in without renewing it (`status(false)`), so opening it needs no network.
- **Tests:** unit tests in `crates/chatgpt` cover PKCE, the authorization address, the callback, the ID token checks on an RSA key `openssl` makes for the test, and sign-in, renewing with rotation and signing out against a fake token server. `tests/e2e/chatgpt.py` (`scripts/repro.py chatgpt`) signs in from the dialog in a debug build against a fake OpenAI on 127.0.0.1 (`NUZKY_CHATGPT_ISSUER`, `NUZKY_TEST_BROWSER` and `NUZKY_TEST_KEYCHAIN`, which release builds never read), restarts the app and signs out.
- **Not verified:** a real sign-in on Windows (a test there keeps a 6 KB sign-in in Credential Manager, replaces it with a shorter one and removes it, which one entry could not hold), and a real Secret Service on Linux.
- **OpenAI's pages and the service:** the discovery document's `scopes_supported` lists only `openid profile email offline_access`, without the two plan scopes the open-source page asks for. OpenAI does not notify an app that was disconnected in ChatGPT's settings; Nuzky notices at the next refresh.

## Phases

1. Headless foundation (done): `crates/session` and `crates/mcp` hosting their own session.
2. One authority: keyed undo steps in the engine, `keep_in_place`, `engine::speech`; `ProjectSession` on the live `Editor` with user edits, events, the writer thread and per-client access; the app on `Host` with its lock, read-only state and recovery dialog; one job system.
3. Transcripts per media file, `get_transcript`, `edit_transcript` and captions from the derived words, in the app and in MCP; the frontend's own transcript bookkeeping goes away.
4. IPC and the `nuzky-app mcp` bridge, then the run UI. Gate: Claude Code in a project folder cuts silences, adds captions and exports, live in the open app, with one Undo and a Stop mid-run.
5. Panel: `crates/agent` (direct CLIs, no ACP) and the dockable React panel, Claude Code first (done), then Codex. Gate: the same task from the panel through Claude Code and Codex, including Stop and Undo.
6. Direct ChatGPT sign-in (signing in, renewing and signing out done, and the panel on it) and other providers.

## Risks

- Retiming after cuts is the hardest correctness problem; `map_words` needs fixtures with speed changes, detached audio, slivers, kept music, transitions and duplicated clips.
- Recognising a whole long recording once costs time up front; if that hurts, store which ranges a transcript covers.
- Blocking manual edits for a whole run may feel heavy; revisit after trying it by hand.
- On Windows the release app is a GUI-subsystem executable. `nuzky-app mcp` still serves an agent over the pipes it is started with: on 24 Oct 2026 a release build answered `initialize` and `get_state` from a plain parent process with `--project` and `--current`, attached to the project open in the app, opened no window and ended when its input closed.
- Agent CLIs and subscription terms change; keep them behind `crates/agent`, recheck the flags on each new agent version, and keep the fail-closed checks.
- The agent's own isolation is its CLI's promise, not a sandbox; the fake agent proves Nuzky passes the flags, the real agent has to be rechecked by hand.
